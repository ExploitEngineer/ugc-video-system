Revonix Studio · implementation plan

Template Library Pipeline

An admin curates a library of After Effects templates. A user browses it with a real video preview, picks one, and writes an ad brief. The backend then reads that template's metadata and generates everything it asks for — copy, images, and a clip of the template's own length — from a single plan, so the pieces describe the same ad instead of looking randomly assembled.

02 What changes

The v1 template code is uncommitted and was never released, so it is free to reshape in place.

v1 · as built

  • The end user uploads their own .aep. No library, no admin, no preview.
  • Only TEXT slots are filled. IMAGE slots keep the template's placeholder art.
  • Template duration is ignored — every run is forced to 15s.
  • Chain is video → template_fill → template_render. The copy is written from the raw prompt, after the clip already cost money.
  • Nothing tells the user what a template will look like before they commit to it.

v2 · target

  • An admin curates a global library; users pick from it.
  • Every template carries an auto-generated preview video and poster frame.
  • A template_plan step runs first and drives every downstream agent.
  • Content IMAGE slots are generated with gpt-image-2, conditioned on the product sheet and the storyboard look. Logos and backgrounds are left alone.
  • The clip matches the template's own composition duration, capped at 15s.

03 Two facts that constrain everything

Both were established during research. Both change the design rather than decorate it.

Seedance durations are a discrete set

Allowed: 4, 5, 6, 8, 10, 12, 15 seconds. Not a range — 7, 9, 11 are rejected.

So "match the template" means snapping up, never down. A clip shorter than its layer ends on a freeze frame; a longer one is simply trimmed by After Effects.

Nexrender has no thumbnails, no custom metadata

There is no template-thumbnail endpoint and no way to attach our own fields to a template.

But a render job accepts preview: true — a fast, cheap, low-res render, mutually exclusive with settings. That is the only preview mechanism, so we generate previews ourselves and own all template metadata in our own table.

Why template_plan is first

Its per-slot output shapes every downstream agent. This is the "metadata and prompts for every agent, according to the template" requirement: one plan, read by the storyboard, the copywriter, the image agent and the video agent.

Why template_fill is late

Placed after the storyboard, the copy can draw on the product brief and the scene transcript instead of guessing from the raw prompt. It is cheap and re-runnable, and template validity was already proven at run creation, so there is nothing left to fail fast on.

Why video is second-to-last

Seedance is the most expensive call in the pipeline, so it belongs as late as possible. Everything that can fail cheaply fails before it.

The orchestrator refactor this needs

The parallel reference phase is hard-wired to currentStep === null, so any step placed before it creates a "re-enter the parallel phase from a non-null step" problem. Rather than special-case that, make person_sheet-as-a-forward-step mean the reference phase: 

const step = run.currentStep === null
  ? (run.pipeline === "template" ? "template_plan"
     : run.adType === "service"  ? "creative_brief"
     : "person_sheet")
  : nextStep(run.currentStep, personUploaded, run.criticEnabled, run.duration, run.pipeline);

if (step === "person_sheet") await runReferencePhase(ctx, tag);  // product ∥ person
else                         await executeStep(ctx, step);

Safe because person_sheet is only ever reachable as a forward step at the reference-phase entry. product_sheet is never a forward currentStep at all — it is generated inside runReferencePhase and checkpointed as person_sheet. The refactor also deletes the existing null-branch duplication, so it is a net simplification.

05 Failure & recovery

The single most dangerous thing in this plan lives here.

regenerate-template must be rewritten, not reused. v1 rewinds currentStep to "video" and re-enters fill → render. Under the new chain video → template_render, that same rewind would re-run the paid Seedance call on every single render retry.

steperror codedisposition
template_planTEMPLATE_PLAN_FAILEDhard fail — nothing downstream ran
template_fillTEMPLATE_FILL_FAILEDhard fail — images and video had not run
template_images—never hard-fails a failed slot falls back to the template's own art
videoVIDEO_*soft-fail to awaiting_regen via the existing ladder
template_renderTEMPLATE_RENDER_FAILEDhard fail — recovery re-runs the render only

Rewind checkpoints, chosen by error code

errorCoderewind currentStep tore-runs
TEMPLATE_PLAN_FAILEDnulleverything
TEMPLATE_FILL_FAILED"storyboard"fill → images → video → render
TEMPLATE_RENDER_FAILED"video"render only — no re-paid video

For the render-only case, also clear nexrenderJobId and delete any partial templated_video row, so the retry submits a fresh job and the newest output surfaces.

Partial image failure is non-fatal by design: one bad image must not destroy a run that has already paid for a video.

06 The template lifecycle

Templates are not runs, so driveRun does not apply. They get their own worker, modelled on the existing one: poll by status, claim by DB lock with a stale timeout, advance one stage, release. 

stateDiagram-v2
  direction LR
  [*] --> registering: "admin uploads .aep/.zip/.mogrt"
  registering --> introspecting: "registered + bytes uploaded"
  introspecting --> previewing: "v3 status = uploaded
structure + metadata built"
  previewing --> ready: "preview rendered,
re-hosted, poster extracted"
  ready --> [*]: "visible in the picker"

  registering --> failed
  introspecting --> failed: "no VIDEO slot,
or more than one"
  previewing --> failed: "render failed or timed out"
  failed --> introspecting: "admin retry"
  failed --> previewing: "admin regenerates preview"

preview_job_id is persisted before polling, so a crashed process never resubmits a paid render — exactly as runs.nexrender_job_id already does for applyTemplate.

Previews are cheap and automatic. We submit one preview: true job with no assets, so Nexrender renders the template's own placeholder content. That mp4 is re-hosted to Supabase and a poster frame is pulled with the ffmpeg already wired up in lib/video/merge.ts. If a template's placeholders are grey boxes and Lorem Ipsum, the admin can upload a hand-picked preview instead.

Why previews cannot be assets rows

assets.run_id is NOT NULL with an FK to runs. A template preview belongs to no run. So previews get their own storage prefix, templates/{id}/…, and their URLs live as columns on the template row.

Indexes. status (the worker polls it); a partial unique index on content_hash WHERE archived_at IS NULL so archiving frees the hash for re-upload; a partial index on status='ready' AND archived_at IS NULL for the hot public list; a GIN index on tags. status is text + CHECK, not a pg enum — matching the existing convention for adType and errorCode, so lifecycle values never need a migration.

08 The Nexrender slot model

What we currently extract, what we throw away, and what we do with each kind.

Two live bugs in the current introspection. It classifies every placeholder precomp as VIDEO, so image placeholders are silently misread. And it drops duration, frame_rate and per-layer geometry on the floor — all three are already in the v3 responses today.

slotdetected fromfilled withstatus
VIDEO av/file with a video extension, or a placeholder precomp the Seedance clip, at clipSeconds exactly one, enforced at upload
IMAGE
content		 av/file with an image extension, or a precomp whose inner layer is an image gpt-image-2, from the plan's subject + slot geometry new in v2
IMAGE
brand / decorative		 same, then classified out (see below) nothing — template's own logo, background, texture never AI-filled
TEXT text layer — its name is its current words the small model, within a derived charBudget reshaped
AUDIO av/file with an audio extension nothing — template's own default v1 scope

Which IMAGE slots actually get filled revised

Not all of them. A generated product photo dropped into a logo layer is wrong every time, no matter how well the library is curated. So every IMAGE slot is classified first, and only content slots are generated.

classsignalsaction
content name matches photo|image|product|hero|shot|still|media|feature, or the LLM judges it a photographic content slot; sensible area (roughly 2–95% of the comp) generate with gpt-image-2
brand name matches logo|brandmark|wordmark|icon|badge, or the slot is tiny (≲2% of comp area) never generate — hard rule, the LLM cannot override it
decorative name matches bg|background|texture|gradient|overlay|shadow|vignette|grain|mask|frame|pattern, or the slot is full-bleed (≳95% of comp area) with no content-ish name never generate — keep the designer's art

The deterministic heuristic runs first and is a guard, not a suggestion. Anything it calls brand or decorative is off the table. Only genuinely ambiguous slots — the ones named PH_2 or Media_3, which is most real templates — get passed to template_plan, where the model sees the slot's name, pixel size and area ratio and decides whether it is a photographic content slot and, if so, what it should depict.

This costs the admin nothing at upload time, which is what you wanted. The admin console still shows the verdict per slot in the table it already renders, with an override toggle for the rare template that defeats both the heuristic and the model. Skipped slots reuse the same code path as a failed slot: the template keeps its own asset.

Asset order is load-bearing

Nexrender applies job assets in array order. Each nx:layer-autoscale must be pushed after the media asset it scales, or it scales the placeholder that is about to be replaced.

A caveat that bites

IMAGE_SIZE_FALLBACK in providers/openai/constants.ts is a lookup keyed by four hardcoded 4K sizes. An arbitrary per-slot size has no fallback entry, so a size-attributable failure would simply throw. We add a generic shrink tier: when the map has no entry, retry at round16(w × 0.7) × round16(h × 0.7). Small, isolated, and it hardens the existing paths too.

09 Frontend surfaces

Cyan/dark, Geist + Space Grotesk, "chat" not "run". Three new surfaces.

Template picker /studio/templates

A grid of cards. Each shows a muted, looping preview that holds its poster frame until the card is hovered and in view. useReducedMotion() disables autoplay outright, and a shared counter caps how many previews decode at once so a long scroll doesn't melt the tab.

Name, duration chip, aspect chip, slot summary (1 video · 3 images · 4 text), tags. Filter by aspect and tags; sort by popular, newest, or name.

Brief /studio/templates/[id]/brief

A Server Component reading templateId from the URL path, so the selection survives refresh, SSR and sidebar tab switches with no localStorage hydration flash.

Reuses create-run-form.tsx. Aspect ratio becomes a read-only "16:9 · from template" row.

Admin console key-gated

Upload via XMLHttpRequest, not fetch — fetch cannot report upload progress and these are 200MB files.

Status pill, preview player, introspected slot table, inline name/tag editing, regenerate preview, archive. Polls every 3s while any row is non-terminal.

The admin gate is a soft guard, not real auth. F8 is not started and the API is otherwise unauthenticated. ADMIN_API_KEY + an x-admin-key header stops a stranger who finds the URL from burning Nexrender credits. It fails closed in every environment when the key is unset, because a misread NODE_ENV in a deploy would silently open template upload to the internet. When F8 lands, only the middleware body changes.

Three shadcn primitives are missing and must be added: input, progress, table. Do not add select — the codebase deliberately uses themed DropdownMenu instead of native selects.
