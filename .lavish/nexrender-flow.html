3 Confirmed: the .aep goes straight to Nexrender

Your call Direct upload to Nexrender's cloud

You upload → our server hands the bytes straight to Nexrender's storage (its presigned upload) → Nexrender introspects + renders. Our Supabase never stores the input project. Exactly as you said.

  • The only Supabase writes for this feature = the OUTPUTS (.mp4 + modified .aep) + any per-layer media you upload (transient).
  • Your generated clip is already on Supabase — we just pass its URL as a render slot. No copy.
✓
You're right — a bigger timeout is a band-aid. The real prod fix is to remove the hop that times out.
  • What timed out: our API server pushing the .aep bytes up to Google Cloud (Nexrender's storage). That server-in-the-middle hop is the fragile part — it also buffers the whole file through our server's RAM, which doesn't scale for big projects.
  • The fix: the browser uploads straight to Nexrender's storage. Our API just asks Nexrender for the one-time upload URL and hands it to your browser; your browser PUTs the file directly. Our server never touches the bytes at all — not Supabase, not even API memory.
  • Why it's the prod-grade answer: browser uploads use the browser's own networking (long, adaptive timeouts + progress bar + resume), not a fixed server cap. It's the same direct-to-storage pattern we already use elsewhere. Big .aep files stop flowing through our server.
  • One thing I verify while building: that Nexrender's storage allows a browser upload (CORS). If it doesn't, the automatic fallback is a hardened server-side upload (stream, no flat timeout, retry) — which works everywhere prod runs regardless.
✅
So I'll: (1) move the upload to browser → Nexrender direct (API only brokers the upload URL; no bytes through our server or Supabase), (2) drop storing the input, (3) add fetching + storing the modified .aep Nexrender returns. Confirm and I build.
